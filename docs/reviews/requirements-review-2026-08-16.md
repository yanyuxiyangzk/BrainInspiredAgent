# MVP 需求评审记录

评审日期：2026-08-16  
评审范围：产品愿景、PRD、系统架构、事件协议、Workflow 规范、记忆、安全、测试及路线图  
评审结论：**有条件通过；后续缺口已补齐，见[冻结就绪报告](../delivery/stage-0-freeze-readiness.md)**

## 1. 结论摘要

现有设计已经明确“受控自治、确定性控制平面、事件驱动、Workflow 执行、分层记忆”的核心方向，可以进入详细设计，但暂不满足“阶段 0 冻结”条件。

冻结前必须完成五项工作：

1. 确认 MVP 目标用户、首个业务闭环、交互入口和部署形态。
2. 将 P0 需求改写为可测试的验收条件。
3. 固化两条端到端场景及异常分支。
4. 冻结 Event、Plan、Task、Workflow 和错误码的 1.0 Schema。
5. 明确恢复语义、数据保留和每日模型预算的默认值。

## 2. 已确认的正确方向

- MVP 不连接真实交易，避免产品验证与高风险执行混在一起。
- LLM 只产生候选计划，Validator/RiskGate 拥有最终授权权。
- 市场阶段、工作负载和健康模式采用正交状态，优于单一三态。
- MVP 使用模块化单体和单一控制事件循环，复杂度与当前阶段相称。
- Workflow 与常驻脑区严格分离，并对递归、超时、并发和副作用设限。
- 记忆区分具体经历和已验证知识，避免将模型摘要直接当成事实。
- 将重启恢复、幂等和可审计性作为 MVP 能力，而不是后期补丁。

## 3. 评审发现

### Blocker：冻结前必须解决

| ID | 发现 | 影响 | 建议处理 |
|---|---|---|---|
| RR-B01 | MVP 同时面向个人研究者、工程团队和策略开发者，首要用户未唯一化 | 交互、部署和验收标准无法聚焦 | MVP 锁定“单人量化研究者、本地单实例” |
| RR-B02 | 首个业务闭环仅有概述，没有输入样本、时间线和确定输出 | 无法据此设计 Schema 和自动化验收 | 冻结“模拟市场摘要”和“夜间复盘”两条场景 |
| RR-B03 | 多项 P0 验收仍是定性描述，如“可被观察”“频率随模式调整” | 完成标准容易争议 | 为每个 P0 增加 Given/When/Then 和数值边界 |
| RR-B04 | 恢复策略提到扫描任务，但没有为节点定义重放类别 | 崩溃后可能重复副作用 | Tool 元数据增加 `PURE/IDEMPOTENT/QUERYABLE/NON_REPLAYABLE` |
| RR-B05 | Event 和 Workflow 有规范，但 CandidatePlan、ApprovedPlan、TaskResult 尚无独立契约 | 决策与执行接口仍可能漂移 | 编写 Plan/Task Schema 1.0 |

### Major：开发内核前应解决

| ID | 发现 | 影响 | 建议处理 |
|---|---|---|---|
| RR-M01 | 愿景将外部命令列入 MVP，但 PRD 标为 P1 | 范围和排期冲突 | 保留最小 CLI 命令为 P0，Web/API 管理能力仍为 P1 |
| RR-M02 | 夜间复盘属于 MVP 关键闭环，但 FR-012 为 P1 | 不能验证“休息不关机”这一核心卖点 | 将最小夜间复盘提升为 P0 |
| RR-M03 | PRD 要求 1000 条/分钟，但没有事件大小、硬件基线和端到端延迟目标 | 指标不可比较 | 定义 4 KiB 以内事件、本地基线机器和 P95 投递延迟 |
| RR-M04 | “计划任务触发成功率 99%”缺少分母和排除条件 | 长稳结果无法解释 | 定义为合法触发窗口内、依赖健康的应触发实例 |
| RR-M05 | 成功标准要求连续 7 天，缺少更快的阶段性门槛 | 反馈周期过长 | 增加虚拟时钟 30 天回放和 24 小时冒烟，7 天作为 MVP 发布门槛 |
| RR-M06 | Attention 的“显著性”没有规则来源和解释字段 | 可能变成不可审计的黑盒 | MVP 先使用确定性阈值，输出 score、rule_id 和 evidence |
| RR-M07 | GoalManager 已进入架构，但 PRD 没有对应需求 | 可能提前建设复杂目标系统 | MVP 只实现固定系统目标和状态，不做 LLM 自主拆解长期目标 |
| RR-M08 | 数据保留建议值尚未决定，删除和大对象管理依赖它 | 数据模型无法完整设计 | 默认 Trace 90 天、聚合摘要长期保存、大对象 30 天 |

### Minor：可在详细设计中解决

| ID | 发现 | 建议处理 |
|---|---|---|
| RR-N01 | “通知”容易被理解成真实外部副作用 | MVP 默认本地 NotificationSink，Webhook 作为可选适配器 |
| RR-N02 | Workflow `delay` 与持久调度边界尚不够具体 | MVP 限制 delay 不超过 60 秒，更长等待转 Scheduler |
| RR-N03 | 日历来源未指定 | MVP 使用可注入 TradingCalendar 和测试日历 |
| RR-N04 | 错误码规范尚未建立 | 按 validation/policy/dependency/timeout/internal 分类建目录 |
| RR-N05 | 缺少配置优先级规则 | 规定默认配置 < 文件 < 环境变量 < 启动参数，策略项禁止运行时任意覆盖 |

## 4. 建议冻结的 MVP 产品定义

### 首要用户

本地部署的单人量化研究者。工程团队和策略开发者作为未来扩展用户，不驱动 MVP 的多租户、权限组织和协作功能。

### 首个业务闭环

```text
可重放模拟行情
  → 确定性注意力规则
  → 候选市场摘要计划
  → 校验与风险门
  → Workflow 生成结构化摘要
  → 本地通知记录
  → Episode 持久化
  → 收盘后生成每日复盘
```

### 交互和部署

- Linux/Docker 单实例；
- CLI 用于启动、停止、状态查询和注入有限外部命令；
- 管理 WebUI 不进入 MVP；
- JSONL 为模拟数据交换格式；
- SQLite 为唯一业务数据库；
- 本地目录保存超限大对象，并由 SQLite 记录引用。

## 8. 需要产品负责人确认的四项决策

建议一次性确认以下默认方案：

1. MVP 面向单人量化研究者，本地单实例运行。
2. 首个闭环采用“模拟市场摘要 + 夜间复盘”。
3. MVP 使用 CLI，不开发 WebUI；内部保留 API 边界。
4. 默认只写本地通知记录，Webhook 作为后续可选适配器。

在这四项确认前，可以继续补详细设计，但不应宣布需求冻结或开始大规模实现。
